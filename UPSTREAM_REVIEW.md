# Upstream fit review, 29 September 2026

Optional background. Start with [one focused review](REVIEW.md); the full issue
map below is available when choosing further contributions.

This is a source and activity review for discussion, not a merge proposal or a claim that the review branch is qualified against current upstream. The checked upstream sources are main [`22d39f24`](https://github.com/GrafeoDB/grafeo/commit/22d39f24be01ecfed1d30093bc395e3f363df7ea) and release/0.5.44 [`e7c48583`](https://github.com/GrafeoDB/grafeo/commit/e7c48583f39306e862414ecfb721ca0adf5b2a97). These are different baselines: [#496](https://github.com/GrafeoDB/grafeo/pull/496) merged the earlier release branch into main; [#530](https://github.com/GrafeoDB/grafeo/pull/530) then added the lower-overhead direct-write path on the release branch, and [#531](https://github.com/GrafeoDB/grafeo/pull/531) remains open at the observed snapshot. The latest published GitHub release is [0.5.43](https://github.com/GrafeoDB/grafeo/releases/tag/v0.5.43), not 0.5.44.

The [current roadmap](https://github.com/GrafeoDB/grafeo/blob/22d39f24be01ecfed1d30093bc395e3f363df7ea/docs/roadmap.md#L21-L44) orders crash safety in 0.5.44, one migrating storage format in 0.5.45, transaction-owned changes in 0.5.46, compact-core storage in 0.5.47, push execution in 0.5.48, and completeness/API parity in 0.5.49. An issue being scheduled or closed is not proof that every part of its wider epic is implemented.

## Review scope

This comparison checked open issues, recently updated and closed issues/PRs,
commits on both active branches, release notes, milestones, review discussions
and all repository discussions. Collection ended at approximately 22:38 UTC on
29 September 2026. The organization project board was unavailable; its issue,
epic and milestone descriptions were accessible. Later activity is outside this
snapshot.

The comparison used source inspection, not a fresh runtime or benchmark campaign.
Test names identify witnesses to inspect; see [REVIEW.md](REVIEW.md) for the
checks actually run on this export. Historical performance results cannot settle
which implementation is faster after reconciliation.
